## Window observation

Read the Native calibration controls separately. A Passed normal control means the observer found no visible attributed window. A Passed allocconsole control means it found the expected visible attributed console window. A Blocked host cell names a missing prerequisite, such as approved login or an isolated host launch. It does not mean the host failed. Passing calibration does not qualify the host.

Run `powershell -NoProfile -File verification/mcp/Invoke-Verification.ps1 -Case windows -Mode Fixture -EvidenceRoot <evidence-root>` for synthetic visibility and attribution controls. Every fixture scenario is labeled synthetic in `windows-calibration.json`. The scenarios cover invisible startup, visible startup, deliberate application AllocConsole, a wrong PID, missing observation, a missing parent chain, and a missing positive control. Fixture success establishes only the scoring behavior.

Run the same command with `-Mode Native` to attempt calibration. `WindowsObserver.cs` compiles through `Add-Type` without a package dependency. It requires a visible window station in a nonzero Windows session and creates a uniquely named desktop with `CreateDesktop`. The observer never calls `SwitchDesktop`, requests desktop switching rights, changes the calling thread's desktop, opens the user desktop, or changes the process window station. It assigns only its own new observer thread to the owned desktop. Control processes receive that desktop through `STARTUPINFO.lpDesktop`. These APIs specify desktop creation, thread assignment, and process placement. [CreateDesktop](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-createdesktopw), [SetThreadDesktop](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setthreaddesktop), [STARTUPINFO](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/ns-processthreadsapi-startupinfow).

The observer creates one hidden anchor window on its own desktop so enumeration must return a known window even when the control has no windows. Each poll verifies that anchor's handle, PID, thread, and hidden state. Hidden IME windows from that same observer thread and native process identity are saved separately as `observerEvents`. Other windows require attribution to the control's observed native parent chain. The anchor is destroyed before the desktop is closed. No application window is hidden, closed, or intercepted by the observer.

The two `TestServer.ps1` controls run in order. Both receive isolated profile and temporary directories under a unique evidence subdirectory, a small explicit environment, inherited input/output/error files, and a 15-second polling deadline. The normal control opens no window, echoes one stdin line, records EOF after that line, writes a stderr marker, and exits 0. Both controls record arguments, a Unicode argument, cwd, an environment variable, and their PID. The deliberate AllocConsole control calls `AllocConsole` through `Add-Type`, records any console window identity, and exits 0 when allocation succeeds. Each successful control stays alive for another 1.2 seconds for sampling. The positive control does not hide its allocated console. [AllocConsole](https://learn.microsoft.com/en-us/windows/console/allocconsole).

`Add-Type` also builds `calibration-control.exe` from the observer source in the evidence subdirectory, with compiler temporary files directed there. This helper uses the Windows GUI subsystem and invokes `TestServer.ps1` through the installed PowerShell assembly without loading profiles. It avoids a startup console without applying window suppression flags that could hide the deliberate console. `CreateProcess` starts the helper suspended, assigns it to an owned job with termination on close, and resumes it after recording its native parent and creation identity. Cleanup closes that job and checks the recorded process identities without terminating an arbitrary PID. The parent environment stays unchanged. The controls do not launch a real host, log in, or read or write the real profile. Desktop isolation does not restrict filesystem or network access, so the observer runs only these trusted controls.

Native calibration passes only if normal has no visible attributed window and AllocConsole has a visible attributed console window matching the positive control's recorded handle and PID. A startup window fails the normal control. A missing window, wrong PID, missing parent identity, failed API, timeout, control error, or cleanup gap prevents calibration. API failures name their step and Win32 error when available. No alternative desktop is tried. The report saves the calibration outcome even when desktop creation, launch, or enumeration fails.

Window sampling uses `EnumDesktopWindows`, `IsWindowVisible`, and `GetWindowThreadProcessId`. Process sampling uses native parent PIDs and creation timestamps, adopting descendants only while the matching parent identity is present. `observationComplete` means the bounded polling loop completed, and `parentChainComplete` means its reported process links were verified. Neither flag proves complete event capture. Samples include handles, window classes, visibility, attribution, elapsed times, parent identities, poll counts, and the maximum polling gap. Short-lived windows and processes can fall between samples. Zero window events never prove no flash, and visibility on an inactive desktop does not establish what a user would see. A console allocation that exposes no visible attributed window blocks the positive control. [EnumDesktopWindows](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-enumdesktopwindows), [GetWindowThreadProcessId](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getwindowthreadprocessid).

Every Native host cell remains Blocked after calibration because approved login and isolated host launch are outside this case. Top-level and host-cell `executionStarted=false` refer to host execution. `calibration.executionStarted` and each control observation separately record actual control launches. Raw results and stream files remain under the unique evidence subdirectory. `report.json` links those files and includes the observed process identities and cleanup checks. `windows-calibration.json` stores the full calibration, attribution, and per-cell gaps.

Each unstarted host cell uses `id` as its target label and lists every missing identity field without inventing a value. A future cell that starts and confirms loading must record `host`, exact `version`, `entry_version`, `command_class`, `cwd_class`, the manifest lookup key `host`, `serversKey`, and `server`, and the digest recomputed from the copy actually loaded. Class values must be derived from that loaded entry using the capability definitions. The entry must come from the rendered artifact merged into the isolated copy and launched by the host. Such an isolated entry is not ccync-managed for ownership. This calibration case performs no merge or host load and establishes no host qualification.

## Passive observation

Run `powershell -NoProfile -File verification/mcp/Invoke-Verification.ps1 -Case passive -Mode Fixture -EvidenceRoot <evidence-root>` for a bounded synthetic observation. The defaults are host `codex`, session `fixture-session`, and one second. Optional `-ObservationHost`, `-ObservationSession`, and `-ObservationSeconds` override those defaults. The host and session must match exactly. The duration must be finite, greater than zero, and at most 3600 seconds. An optional `-EventFixturePath <json-file>` supplies a synthetic v1 source. The source is read once during the interval, so later events can be missed. The output contains sanitized v1 events and provenance with start, end, and gaps. Observation markers describe the fixture observer, not a native stop. Prior events are not visible. The synthetic observer version is fictional.

The linked `passive-report.json` records `boundedStop`, elapsed and requested seconds, and integer `interventionCounts` for use, connect, launch, write, reload, notify, restart, shutdown, and desktop. These counters describe actions by the fixture observer, not events from the source. Each run checks that they are zero and tests each counter with an independent synthetic intervention. The synthetic tests do not perform those actions. Their results appear in `report.json`.

Native passive capture remains Blocked because no verified logical event source is available. Before observing an existing user session, P7 must separately authorize the exact host, session, and time window. The passive entry injects no faults, sends no use, connect, or launch requests, writes no configuration, sends no reload or notification, restarts or shuts down no agent, and opens no desktop. It writes only local evidence. Ordinary doctor reads a supplied file and does not start observation. No daemon or automatic session monitoring is provided.

## Event fixtures and native gaps

Run `powershell -NoProfile -File verification/mcp/Invoke-Verification.ps1 -Case events -Mode Fixture -EvidenceRoot <evidence-root>`. Add `-EventFixturePath <json-file>` to replay a synthetic v1 event file. The input is limited to 256 KiB and 1,000 events. The output `events.json` contains only v1 fields. Identity strings are replaced with consistent aliases, extra input fields are discarded, and event digests are omitted. The separate `event-provenance.json` identifies the source as synthetic. Run `ccync doctor --mcp-evidence <evidence-root>/events.json` to analyze the normalized file. Missing parent references remain missing. A logical event can represent an attempt without a process ID.

Every fixture run also writes four independent synthetic control files. They cover a native-config source, an HTTP attempt without a local server PID, a pre-handshake failure, and a dropped connection. Each contains only normalized v1 logical events and is identified as synthetic in `event-provenance.json`. The control names provide the scenario context: v1 has no fields for transport, PID, handshake phase, or the cause of a connection drop. Therefore the event rows alone cannot prove those details. Replay any control file with `ccync doctor --mcp-evidence <control-file>`.

The Native case reports each host's version from the recorded capability table when available and marks its event probe Blocked. It does not launch a host or claim a current version. The table does not establish a logical event feed, clock calibration, or native fault controls. Process counts and timing do not fill those gaps. Native source capture and rendered fault-entry merging remain unimplemented. Fixture success does not establish Native capability.

## Capability checks

Run `powershell -NoProfile -File verification/mcp/Invoke-Verification.ps1 -Case capabilities -Mode Fixture -EvidenceRoot <evidence-root>`. The separate `capabilities.json` uses synthetic facts for five hosts. It records `command_class`, `cwd_class`, and `entry_version`. An optional `-CapabilityFixturePath <json-file>` supplies objects keyed by `claude`, `codex`, `copilot`, `opencode`, and `agy`. Each object accepts boolean `isolation`, `login`, and `headless` and numeric `usage`, `allowance`, `attemptCost`, `attempts`, and `attemptCap`. The check blocks if a fact is missing, if an attempt exceeds the host's quarter allowance, or if its attempt cap is reached. These values are test inputs and do not establish actual capability.

Native capability discovery runs one bounded `--version` command per available host in a fresh empty isolated profile. It inventories the isolated `USERPROFILE` and `APPDATA` before and after each version command and writes `bootstrap.json`. The version record includes the command, exit code, exact standard output and SHA-256 of the discovered launcher. For script launchers the hash identifies the launcher, not its underlying runtime or package. Inventories contain relative paths, metadata, hashes and read gaps. Changes are candidates for review, not proof of Native isolation.

The bootstrap also runs bounded `claude mcp list`, `codex mcp list` and `opencode mcp list` in their isolated profiles. It records exit status and whether the output matches a known zero-server response, without retaining listing output. No verified noninteractive listing is recorded for Copilot or agy. These listings do not prove the actual loaded configuration path. OpenCode's separate default-path check remains outstanding. That check must clear `XDG_CONFIG_HOME` and overrides and keep configuration roots distinct. A confirmed mismatch with the managed path requires a named product follow-up.

`host-state-classification.json` records the observed version and listing metadata, sourced credential location classes, explicit missing prerequisites, and the fixed `command_class`, `cwd_class` and `entry_version` values. A credential location from documentation describes a supported storage method, not an observed login. Codex and Copilot can use other credential stores. Credential contents are never recorded. Each host has `allowedVolatile` and `excludedEphemeral` arrays. The capabilities case writes only those arrays to `classification-<host>.json` in the evidence directory and validates each derived file with the isolation loader. Empty arrays do not claim that the host has no volatile or coordination state. Unobserved coordination items remain gaps. A reviewer must approve observed exact classifications before Native verification, and a later run can pass the approved derived file with `-ClassificationTablePath`.

The bootstrap does not use `-HostProfileRoot`, log in, invoke a model, or establish login, usage bounds, stop settings, event sources, desktop capability or the actual load path. These gaps block every Native host. Native login requires a dedicated profile under `%LOCALAPPDATA%/ccync-verification/host-profile/<host>`, with separate `home` and `appdata` directories. Login commands for all hosts are not yet verified. Do not write credentials to evidence or copy the real profile. Fixture success does not authorize a Native cell.

## Fixture commands and coverage

The isolation case inventories `<evidence-root>/fixture`, launches a real child, then inventories again. It writes `before.json`, `after.json`, `diff.json`, and `child.log`. The report contains the observed child environment, PID, parent PID, native creation timestamp, and cleanup results. `-FixtureCommand '<PowerShell code>'` runs trusted fixture code in that child with the fixture directory as its working directory. This is environment isolation, not an operating-system sandbox. Fixture commands must use owned fixtures and must not invoke real hosts or modify the real profile. `-OmitFixtureVariable CCYNC_HOME` exercises an executed missing-variable failure.

The child gets isolated `USERPROFILE`, `HOME`, `APPDATA`, `LOCALAPPDATA`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `XDG_CACHE_HOME`, and `CCYNC_HOME`. `HOME` equals `USERPROFILE`. The entry clears `OPENCODE_CONFIG_CONTENT`, `OPENCODE_CONFIG`, `CCYNC_SKILLS`, and `CLAUDE_CONFIG_DIR`. Fixture host defaults are `CODEX_HOME=<USERPROFILE>/.codex`, `COPILOT_HOME=<USERPROFILE>/.copilot`, and `OPENCODE_CONFIG_DIR=<APPDATA>/opencode`. Parent environment values are preserved.

Cargo clears all four host variables. It preserves the real `CARGO_HOME` and `RUSTUP_HOME`, pins `CARGO_TARGET_DIR` to the worktree's `target`, and records `CCYNC_RECORDED_PYTHON`. It uses an existing recorded Python path when supplied, otherwise it resolves `python` from PATH. Missing tool prerequisites block execution. Cargo commands must start with `cargo ` and use plain arguments. Shell operators and quoted arguments are rejected. The report records each observed test target and summary. A target without a summary or with zero executed tests stays NotRun. A test command without a completed nonempty target fails verification. The overall cargo exit status is recorded independently.

`-SelfTest` exercises two reruns, inherited overrides, missing variables, persistent changes without repair, volatile patterns, protected-path rejection, Claude MCP subtrees, locked coordination files, new read gaps, dedicated profile cleanup, owned descendants, an unowned PID, background changes, cargo environment and target reporting, and blocked cases. Each assertion group appears in the top-level report. Nested directories retain individual execution reports. This focused suite runs `cargo test -p mcp --lib`. Full workspace regression remains a separate check.

## Classifications and unchanged claims

Supply `-ClassificationTablePath <json-file>` with this shape:

```json
{
  "allowedVolatile": ["logs/**", "sessions/*/log.txt"],
  "excludedEphemeral": ["coordination.lock"]
}
```

Patterns are relative to the inventoried host root and use `/` separators. Matching ignores case. `*` matches characters within one segment. `**` occupies a whole segment and spans zero or more segments. It requires at least one preceding fixed segment. Absolute paths, traversal, unsupported wildcard syntax, and broad patterns that could cover protected state are rejected. ExcludedEphemeral entries must be exact paths. No table means no exclusions.

The managed-target catalog follows `live_mcp_target_paths_inner()` and `live_mcp_target_paths()` in `crates/mcp/src/lib.rs`: `.claude.json`, `.codex/config.toml`, `.copilot/mcp-config.json`, `.gemini/config/mcp_config.json`, and the platform configuration directory's `opencode/opencode.json`. OpenCode targets are protected relative to the configuration root as `opencode/opencode.json` and relative to the profile root under `.config`, `AppData/Roaming`, and `Library/Application Support`. Literal patterns and matching `*` or `**` patterns are rejected before child execution. The table loader also rejects credential paths and ccync state subtrees. Conservative rejection of credential-related names and wildcarded top-level directories prevents ambiguous classifications. Classification is decided before reparse-point handling. Reparse points are never followed. Their target is recorded, and a changed unclassified target fails comparison.

Persistent files compare relative path, SHA-256 byte digest, size, and modification time. File reads allow `FileShare.ReadWrite | FileShare.Delete`. `.claude.json` compares only normalized `/mcpServers` and `/projects/*/mcpServers` subtrees, including property presence and array order. Its other fields are explicitly excluded from unchanged claims. JSON object property order is normalized.

AllowedVolatile changes do not fail the comparison. The report lists matching observed paths in `allowedVolatile`. The diff lists their changes separately and excludes them from `unchanged`. Read errors on volatile paths still count as gaps. An unreadable exact ExcludedEphemeral file records its path, type, available metadata, and read error. Readable coordination files receive ordinary comparison. New read gaps never become exclusions. An item's failure preserves other items' inventory. Baseline gaps block child execution. Gaps first observed after execution fail the run.

## Profiles and process safety

`-HostProfileRoot <dedicated-profile>` copies its `home/` and `appdata/` into this run's temporary directories outside the evidence root. Only that dedicated profile is copied. The entry rejects the real home as a profile root and rejects reparse points in the copy source. The source profile is preserved. The temporary copy is deleted at the end, including after failure. If cleanup fails, the report fails and lists the remaining path. Credentials are not included in inventories or environment evidence. Use synthetic profile content for fixture runs. Native host login and its per-host default profile directory belong to later Native integration.

Process discovery uses Windows native parent PID and creation timestamps. Descendants are adopted only while a matching live parent identity is present. Cleanup checks recorded identity again and refuses unowned PIDs or reused identities. The entry never stops pre-existing sessions or repairs observed state changes. Process sampling does not establish complete short-lived process capture or Native host qualification. Native integration must supply the approved exact classification table and full real-machine baseline before any host launch.

The future Native baseline must cover real ccync configuration and state, `.agents`, `.claude.json`, `.claude`, `.codex`, `.copilot`, both OpenCode configuration locations, `.gemini`, and tested project configurations. Fixture inventories do not establish that coverage. Unexecuted safety premises remain unproven.
