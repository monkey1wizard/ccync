# ccync 安全性

## 支援版本與通報流程

安全性修正以目前受維護的最新版本為主，舊版本不提供個別修補程式。若發現具備利用風險的安全漏洞，請經由 GitHub 儲存庫的 Private Security Advisory 提出私下通報，切勿直接建立公開 issue。通報時請附上受影響版本、完整重現步驟、潛在威脅評估與已知的暫時緩解措施。專案維護者將協調確認並安排揭露時程；本專案並未承諾固定之回覆或修補時限。

## 受保護資產與角色

ccync 著重保護之資產包含：使用者輸入資料、MCP 機密值、外掛來源設定與鎖定版本、各項所有權證明，以及各代理實際生效之原生設定。外部來源儲存庫、本機操作者、ccync 執行檔、代理主機與第三方外掛分屬不同信任角色。來源儲存庫內容可供下載，並不代表其中的腳本具備執行授權，亦不授權 ccync 任意異動或刪除目標路徑中的檔案。

## 信任邊界

- `~/.ccync/config.json` 與 `plugins.json` 屬於使用者輸入；`cache/` 與 `build/` 則屬可重新產生的衍生資料。
- 原始 MCP 定義與 `${VAR}` 佔位符在完成安全解析前均視為不可信來源；復原交易日誌僅記錄變更前後的指紋，絕不儲存解析後的明文機密值。
- 各代理的實際設定檔屬於本機共用資源，ccync 僅合併自身管轄之欄位；在缺乏明確所有權證明的情況下，絕不擅自刪除既有項目。
- 發行檔案必須符合 checksum 校驗、相容平台以及 static CRT 靜態連結規範。若本機執行檔由套件管理器安裝，ccync 不會逕行越權自我更新。

## 攻擊面與安全不變條件

### 發布權限邊界

目標發布控制器是私有 GitHub。公開儲存庫只接受受防護發布流程產生的 curated 快照；GitLab 僅作備份，且必須停用發布 writer。控制器契約會核對公開目的地。若 tag 已存在或無法查詢，流程會拒絕發布。流程會以原子方式推送快照分支與對應 tag。公開推送憑證只在最終發布步驟藉由 ephemeral askpass 提供。只有在具備 workflow run 與遠端 ref 證據時，才能宣稱 hosted 設定或發布成功。

Git clone、封存檔解壓縮、子路徑選取、外掛清單、MCP 啟動指令與環境變數、符號連結或 junction、設定檔解析、備份還原與安裝流程，皆可能接觸不可信輸入。檔案路徑絕不得逸出或跳脫預期根目錄。一旦遭遇未知或存在語意歧義的狀態，ccync 必須立即中止該項操作。

檔案寫入須經由暫存檔重新命名或暫存目錄原子交換完成；檔案刪除則必須具備所有權證明，確認項目確實歸 ccync 管轄。當單一目標或個別伺服器發生異常時，執行結果必須明確指出失敗對象，絕不可將 `NotRun` 視同成功。
