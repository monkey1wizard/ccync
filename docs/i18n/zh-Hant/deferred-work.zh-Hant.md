# 已知待辦

此處記錄可經由目前程式碼或測試案例證實、但尚未於現有版本解決之技術債、工程缺口與重啟評估條件。清單內容並非即期交付之功能承諾；相關問題獲得修復後，負責該項變更的維護者應主動更新或移除對應項目，避免文件殘留過時資訊。

## 本機狀態與原子寫入

- **P7 生效表面搬遷仍延後。** 在能以已驗證的所有權與復原證據安全重新建立主機註冊前，`~/.ccync` 下已註冊的路徑維持原位。範圍包括 `plugins/`、來源連結、`build/render/`、`build/active/`、`data/` 與安裝收據。
- **P5 套件快照匯出仍延後。** 可攜套件快照必須從私有狀態衍生，依封閉的可攜規則准入，並在私有狀態之後寫入。快照不得成為路由或所有權權威。憑證與未分類資料須保留在私有儲存。
- 匯入流程中仍有少數鎖定檔更新操作採用標準檔案寫入。後續若重構此處流程，應全面改用共用之原子寫入機制，並補足寫入中途遭中斷之復原測試。
- 執行快取清理時，若某特定項目缺乏確定之現用版本、但存在多個候選快取目錄，ccync 會選擇全數保留並提出警示。若未來擬實作自動挑選清理機制，必須具備可驗證之所有權與版本證明，絕不可僅憑檔案修改時間逕行判斷。
- 身分重新綁定仍列為待辦。若管理器能證明套件身分變更後仍對應至原先受管理的安裝，且不會接管使用者自行管理的安裝，即可重新評估此項工作。
- 跨程序保存已載入的工具世代仍列為待辦。若支援的操作需要在程序重新啟動後偵測或復原世代變更，即可重新評估。
- `ccync upgrade tool:<id>` 維持 beta，所有套件更新關卡皆為 `Gated`。只有真機驗收通過後才應重新開啟。2026-10-01 的 Windows 驗收留下三個未結問題：已提交的 `tool refresh --json` 與 `upgrade --json` 會在 JSON 文件之前於 stdout 印出投影說明文字；兩次 `upgrade tool:rtk` 皆以管理器結束代碼 `101` 結束，原因未確認，且升級路徑會丟棄管理器的 stderr；復原只用注入的日誌演練過。

## 投影與主機行為

- `ccync sync` 在尚未初始化的機器上以 `1` 結束，而 `ccync init` 的拒絕與取消以 `64` 結束。當腳本需要同一個結束碼時，請讓 `sync` 與[指令參考](commands.zh-Hant.md)中的 init 結束碼矩陣對齊。若操作者回報腳本無法分辨兩者，即重新開啟此項。
- OpenCode 設定檔路徑之環境變數覆寫機制，過往曾在實機測試中發生環境隔離失效問題。若修正此處邏輯，相關驗收測試絕不可觸及或汙染操作者的真實家目錄。
- 第三方上游安裝程式可能順著 Antigravity 之 junction 連結，直接改寫 ccync 所建置的輸出目錄。在推動改善方案前，須先行決策是由 ccync 主動防護輸出根目錄，抑或由安裝程式之包裝腳本限定僅向單一主要來源寫入。
- 目前兩階段投影僅於首次遭遇失敗時退回實體目錄複本。若未來改為持續重試符號連結，仍必須依循先建立暫存目錄再執行原子交換之原則，絕不可預先移除目前正常運作中的根目錄。
- 啟動時解析的 MCP 套件參照由 `feat-mcp-first-class-intake` 負責。該功能定義 MCP 套件參照在啟動時的解析方式，以及所有權與機密邊界後，即可重新評估此項工作。

## MCP 與發行管線

- MCP `--dry-run` 報告可進一步細化逐主機、逐伺服器的預覽明細。未來擴充功能時，若存在尚未解析之機密值或主機設定檔無法讀取，絕不可將該項目誤計入整體成功統計中。
- **P7 codegraph 與 Graphify 移交仍待處理。** 規劃透過新的 personal MCP 清單、明確選定的 hosts 與完整 preview 接入 codegraph。Graphify uv 遷移不是前置條件。記錄實作 commit 與 build、已安裝 binary 的 version 與 hash、各 host 組合的資格結果與證據，以及各項 source、destination、owner、gap 與未知項。計畫與 fixture 結果不能使 host 取得資格，也不能證明實機連線。
- 2026-11-12 的資格檢查將五個 Native host 均列為 Blocked，沒有產生候選項。雙語復原 replay 使用隔離 fixture，並未復原真實歷史。作出實機決策前，請重新核對保留的證據。
- 分別盤點 Graphify 外部套件、tracking record、來源 skill、每份 projected copy 與 rollback snapshot，記錄各自的 ownership 與預定去向。同名或內容相同不授予撤回權。保留 foreign content 與仍被 active 或 rollback state 參照的 snapshot。codebase-memory MCP 是獨立決策。每次安裝、部署、sync、復原或移除都須取得該精確操作的授權。此移交不代表已執行任何此類操作。
- 新版 layout 與 RTK tee 的觀察只以 read-only 證據移交，另行決定處置。歷史 D-68 cleanup 維持已解決。不得推定有新殘留，也不得將未執行的安全前提視為已證明。

### 離線 MCP 復原檢查清單

在復原生效表面前，請使用者提供同一使用者與主機的過往紀錄。歷史數量本身無法識別曾發布的伺服器。其他帳號或主機的紀錄只能作為線索。不要將憑證或解析後的機密值複製到清單。

1. 保持提供的紀錄不變。記錄每筆來源位置與摘要、使用者、主機及伺服器名稱。若沒有伺服器名稱，保留主機層級的列並記錄缺少的證據。
2. 在每個隔離主機上執行 `ccync sync --dry-run`，逐列比對完整預覽與過往紀錄。記錄目前狀態、明確選擇、可能新增的程序數及待處理動作。對 stdio 而言，每個新啟用的主機工作階段都可能啟動一個程序。預覽不能證明程序已啟動或連線。
3. 將各列分類為確認缺失、歷史不足、已停用或排除、存在，或同名衝突。只有同一使用者及主機的證據識別出先前發布的來源與伺服器，且目前狀態顯示缺失時，才能確認缺失。同名但來源不同的項目屬於衝突，不能證明缺失項目存在。未解決的列與未知變更維持待處理。
4. 檢查完整差異，包括其他主機與項目。檢查不會寫入設定，也不會選取復原項目。另行取得單一項目的授權後，先以 `ccync sync --reselect-mcp SOURCE SERVER HOST --dry-run` 預覽並檢查完整差異。若已獲授權，再對該項目執行不含 `--dry-run` 的相同指令。一般發布檢查仍適用。不要隱含選取其他項目。

以下為虛構證據。`A` 與 `B` 是同一使用者的隔離主機環境。`sha256:a` 與 `sha256:b` 代表已記錄的摘要，並非實際 SHA-256 值。每個來源位置指向提供的過往紀錄，並非建立紀錄的指令。此範例假設下列預覽觀察結果。

| 過往紀錄與使用者 | 主機 | 伺服器 | 預覽／目前狀態與選擇 | 分類 | 可能新增程序 | 待處理動作 |
| --- | --- | --- | --- | --- | --- | --- |
| `records/A`、`sha256:a`、使用者 `lee` | `claude` | `atlas` | 先前從來源 `personal` 發布，目前缺失且保留待重新選取狀態 | 確認缺失 | 若選取，每個作用中工作階段 1 個 | 檢查完整差異，並另行取得 `personal atlas claude` 的授權 |
| `records/A`、`sha256:a`、使用者 `lee` | `claude` | `birch` | 先前已發布，目前明確停用 | 已停用或排除 | 停用期間為 0 | 維持停用 |
| `records/A`、`sha256:a`、使用者 `lee` | `claude` | `cedar` | 先前已發布，目前仍存在 | 存在 | 未變更的項目為 0 | 不選取復原 |
| `records/B`、`sha256:b`、使用者 `lee` | `codex` | `atlas` | 先前從 `personal` 發布，目前存在的 `atlas` 屬於其他來源 | 同名衝突 | 解決前未知 | 考慮復原前先釐清身分並解決衝突 |
| `records/B`、`sha256:b`、使用者 `lee` | `codex` | 未知 | 只有歷史數量，沒有伺服器名稱 | 歷史不足 | 未知 | 保留主機層級的列並取得具名紀錄 |

僅第一列另行取得授權後的操作為 `ccync sync --reselect-mcp personal atlas claude`。其他列維持待處理或不變。這些範例不能證明任何機器上的實際復原候選項目。
- 發行檢查高度依賴執行平台與環境。若缺乏適用的 CI runner，對應之驗證檢查必須明確標註為 `NotRun`，不可擅自推論驗證合格。針對 Windows static CRT 靜態連結之相依性檢查，屬於不可退讓之必要門檻。
- Hosted CI 會在 Ubuntu 與 Windows 執行完整 workspace 測試，不依名稱略過任何測試，也會在匯出的公開快照中執行。
- WinGet 遠端更新探索仍列為待辦。若 ccync 必須從遠端 WinGet 來源探索更新，而非取決於本機套件狀態，即可重新評估此項工作。
- 非 Windows 平台的 pipx 與 Homebrew Phase B 證明仍列為待辦。尚未證明的 Phase B 門檻維持 `gated`。備妥適用的非 Windows runner 後，再測試兩種套件管理器。測試範圍包括安裝、更新與復原。完成測試後，即可重新評估證明工作。
- 核准能力範圍以外的其他生命週期工作仍列為待辦。只有在受支援的平台、套件管理器或使用者流程有此需求，且所有權、復原與機密處理均可驗證時，才重新評估。最終驗收收據會列出目前門檻狀態；本文件不重複可能過時的門檻清單。

## 匯入技能的獨立副本

- `crates/ccync-cli/tests/sync_cli_matrix.rs` 預期，從某個來源代理根目錄匯入的技能，會以獨立副本發布到每個已選的讀取者根目錄，但已經存放該技能的根目錄除外。登錄表在 `directSkillProjectionPaths` 記錄每份副本。重複執行 `sync` 會保留這些副本，`uninstall` 會移除它們。
- 這項預期記錄的是目前行為，不是已確認的設計決定。計畫文字以「可以」允許獨立發布，也沒有指名來源代理根目錄，所以負責人尚未確認 Claude 根目錄的技能是否應該出現在 `~/.agents/skills` 與兩個 `~/.gemini` 技能根目錄。這項測試修改是獨立的提交，可以單獨還原。
- 尚未驗證：使用者刪除副本後 `sync` 是否會補回，取消選取目標、重新選取與移除來源時這些副本如何處理，以及這些副本是每次 `sync` 從正本重新產生，還是只在 `init` 寫入。
- 負責人決定預期行為後，再重新評估此項。若不應產生副本，請還原測試預期並修改引擎，讓匯入的技能留在自己的根目錄。若應產生副本，請把規則寫入[外掛](plugins.zh-Hant.md)，並保留此預期。

修改上述任一行為時，請同步更新負責規範該主題的核心文件：[設定與診斷](setup.zh-Hant.md)、[架構](architecture.zh-Hant.md)、[MCP](mcp.zh-Hant.md) 或 [指令參考](commands.zh-Hant.md)。
